# vin — Roadmap

Feature roadmap; milestones are in rough dependency order. Item IDs (`2.3`) are stable — don't renumber when items are added, finished, or dropped; a new item takes the next free number in its milestone, and a dropped item's number is never reused (1.13 and 2.19 were dropped). An item not yet accepted ends with *(proposed)*. Keys for any of these features go in [CONTROLS.md](CONTROLS.md).

Section names in parentheses (Tech Stack 2, Architecture, Glossary, …) refer to [CLAUDE.md](CLAUDE.md).

## 0. Foundation

- [x] 0.1 Git repo on `master`, branch per feature/fix.
- [x] 0.2 Project skeleton — CommonJS backend, ESM UI, `Vin` entry point, `node --test`.
- [x] 0.3 JSX build with esbuild (`npm start`, `npm run dev`).
- [x] 0.4 JSDoc, `jsconfig.json`, and `@types/*` for VS Code autocompletion.
- [x] 0.5 `npm run typecheck` — TypeScript as a dev-only checker of the JSDoc types (`tsc --noEmit`; code stays plain JS); run it with the tests before merging.
- [x] 0.6 Tests for `.jsx` components — a module hook transpiles JSX on load; ink-testing-library 4 works with Ink 7.
- [x] 0.7 `prepare` script that builds `dist/` (it's git-ignored), so a fresh `npm install` + `npm link` gives a working global `vin`.
- [x] 0.8 Debug log file (`VIN_LOG=<file>`) — stdout/stderr belong to Ink while the TUI runs.

## 1. Core architecture

- [x] 1.1 `Handler` base class — name, sub-handlers nested to any depth, dotted-path addressing (`handler.subhandler.method()`), lifecycle (init/dispose).
- [x] 1.2 State API — `this.state` as a deep proxy that records edits as path-based patches; `this.update(state)` for full replacement; patches from one tick batched into one message.
- [x] 1.3 UI store and `useSelector` — a per-window mirror of handler state that applies patches; built on React's `useSyncExternalStore`, so only components reading a changed path re-render.
- [x] 1.4 In-process transport and `ui/tui/handler.js` (`init(handlerName)`) — the TUI's direct proxy, using the same message shapes the JSON-RPC transport will (4.5).
- [x] 1.5 Event system — `Vin`-level bus for events between handlers (and later plugins); subscriptions released on dispose.
- [x] 1.6 Contribution registry — the one extension-point mechanism for commands (with `tui`/`cli` surface flags), context-menu entries, and keybindings.
- [x] 1.7 Keybindings — keys map to registered commands; multi-key sequences; scoped per window/mode; user remapping in config.
- [x] 1.8 TUI window manager — overlays (see Glossary) stacked over the main view, with focus and key input routed to the topmost one.
- [x] 1.9 Configuration — `config.json5` in the project root, user values merged over defaults declared in code, validated with readable errors.
- [x] 1.10 Path module — parses Windows native (`C:\…`) and Git Bash (`/c/…`) forms, UNC shares, and `~`; displays Unix-style (`~/…`, `/c/…`), keeping the native form for the OS.
- [x] 1.11 `FileSystemProvider` and the local-disk provider — the interface from Architecture plus `createDirectory`, `copy`, and streamed reads/writes, so large and cross-provider copies never buffer whole files; resources addressed by URI whose scheme picks the provider (as in VS Code).
- [x] 1.12 Error reporting — expected failures (`EACCES`, `ENOENT`, `EBUSY`, …) shown as messages in the UI, never crashes; unexpected ones also go to the log (0.8).
- [x] 1.14 Standard dialogs — confirm, text input, and choice list as reusable windows (1.8), with their keys, for delete, rename, create, and conflict prompts (2.7), and passphrases (5.2). Built-in handlers with their own Ink components; the declarative vocabulary foreign plugins build UI from stays in 4.6.

## 2. Local file manager (MVP)

- [x] 2.1 Main window — two-pane split view (the panes as sub-handlers of its handler), switching the active pane, optional single-pane mode.
- [x] 2.2 Directory listing — each pane lists its directory (`entries`, and a `cursor` 2.3 moves): `readDirectory` gives names and types at once, then `stat` fills in size, modified time, and whether it's executable, 256 entries per update, so a huge directory opens instantly (20 000 files: listed in ~60 ms, details in ~0.3 s). Directories first, then names in natural order, until 2.11. Only the rows that fit are rendered (Tech Stack 2), scrolled to keep the cursor in view. Columns: the name with `ls -F` markers (`/` `@` `*` `|` `=`), size (`4.2 K`), modified (`Sep 24 14:03`, or the year if it isn't this one) — the last two dropped as a pane narrows; a long name is cut at the end, keeping its marker. Colors from papercolor-dark (`pane.directory`, `pane.link`, `pane.executable`, …; the cursor's line `pane.cursorActive`, and `pane.cursor` in the other pane). Executable means an execute bit on Unix, and `.exe .com .bat .cmd .ps1` on Windows (not `PATHEXT`, which marks every `.js`). No `..` entry: going up is a key (2.3).
- [x] 2.3 Navigation — `pane` commands: cursor up/down (`j`/`k`), first/last (`g g`/`G`, Home/End), a page (`ctrl+f`/`ctrl+b`, PageDown/PageUp — a page less a row, so the view's edge row stays in view; the UI reports its height with `setPageSize()`) or half (`ctrl+d`/`ctrl+u`); `open` enters a directory (`l`, right arrow, Enter — on a file, a message until 2.5 opened it); `toParent` (`h`, left arrow, Backspace, `alt+up` — no `..` entry) puts the cursor on the directory you came from; `home` (`~`); `back`/`forward` (`alt+left`/`alt+right`, and vifm's `ctrl+o` — its `ctrl+i` is Tab to terminals) through a per-pane history of 100, which going somewhere new cuts short, as in a browser, and which drops a directory that can't be listed any more; `navigate(pathOrUri)`, relative to the pane's directory. Every directory left remembers the cursor's entry, so coming back puts it there. A directory that can't be read is reported and the pane stays where it was.
- [x] 2.4 Windows drives — the parent of `C:\` is the list of drives, `file:///` (`paths.drives`), shown as `/` with each drive by its letter (`c/`, `d/`), as the Unix-style paths below it (`/c/…`) have it; `/` typed goes there, and `file:///c/…` reads as `C:\…`. Listed by `fsutil fsinfo drives` (~20 ms, no elevation; mapped network drives too, disconnected ones included, as Explorer shows them), or, failing that, by probing each letter. Each drive shows its free space (`stat` of any root gives `free`, from `fs.statfs`) and no time. A disconnected network drive takes seconds to answer, so a pane's details now show what has come every 200 ms while an entry is slow, instead of waiting for the whole batch.
- [x] 2.5 Opening files — `pane.open` (Enter, `l`, right arrow) enters a directory or opens a file with the OS default app, as a double click does (an executable runs): PowerShell's `Invoke-Item -LiteralPath` on Windows (the path in an environment variable — `cmd`'s `start` would parse `&`, `^`, `%` in names), `open` on macOS, `xdg-open` elsewhere, never through a shell (`src/open.js`). The launcher runs detached, not awaited, so keys go on; its failure (no such file, `xdg-open` missing) is reported when it comes. `pane.enter` only enters directories, for users who'd rather `l`/right did nothing on a file (`{ key: 'l', command: 'pane.enter' }`). Only files on this computer, for now; a FIFO, socket, device, or broken link says why it can't be opened.
- [x] 2.6 Selection — `pane` state `selected` (names, in listing order) and `range` (where a group being selected starts; it ends at the cursor): `toggleSelection` (`v`, then down), `groupSelection` (`shift+v`, ended by it or `v`, which add the group to the selection — so groups and single entries combine), `unselect` (Escape: the group first, then everything), `selectAll` (`ctrl+a`), `invertSelection` (`*`; vifm's `ctrl+i` is Tab to terminals). Selected rows get a `✓` in a gutter shown while anything is selected, and `pane.selected` (vifm: Selected); the bottom border counts them (`GROUP: 3 selected`). Another directory clears the selection; reloading the same one keeps what's still there. Operations act on `pane.targets`: the selection, or the entry under the cursor when nothing is selected.
- [x] 2.7 File operations — `pane` commands on `pane.targets`: `copy`/`cut` (`y y`/`d d`, `ctrl+c`/`ctrl+x`, `cmd+c`/`cmd+x`) put entries on vin's clipboard (`src/clipboard.js`, one per `Vin`, `this.clipboard`) and their native paths on the OS clipboard as text (PowerShell's `Set-Clipboard` — `clip.exe` garbles non-ASCII names — `pbcopy`, `wl-copy`/`xclip`/`xsel`; a failure reported once), ending the selection; `paste` (`p`, `ctrl+v`, `cmd+v`) copies or moves them here, and `pasteLinks` (`shift+p`) makes symlinks (`createSymlink`, a new optional provider method; on Windows without Developer Mode a directory gets a junction, a file an explanation). Pasted text that is a list of paths is a paste too (`Pane#onText`) — vin's own, so Windows Terminal's `ctrl+v` works, cut ones included, or any others as copies. `main.copyToOther`/`moveToOther` (`y p`/`d p`) through `pane.copyTo`/`moveTo`. A name taken asks (`ChoiceList`): overwrite — or merge a directory into a directory, entry by entry — skip, keep both (`name (2).txt`), each for all too, or cancel (`src/handlers/main/pane/operations.js`); a copy into its own directory keeps both without asking. `delete` (`shift+d shift+d`, `Delete`) is permanent after a question starting on Delete (`pane.confirmDelete`), unless the trash (2.9) is on; `shift+Delete` and deleting inside the trash are permanent. `rename` (`c w`, `c c`, `c a w`, `c i w`) and `create` (`a`; a trailing `/` makes a directory, inner ones the directories on the way) in a `Prompt` that refuses a name taken. A pane reloads after its operations — the cursor staying on the row of an entry gone — and emits `changed`, for `main` to reload the other pane. They run as jobs (2.10), with progress and cancel.
- [x] 2.8 Bulk rename — `pane.rename` (`c w`, …) on two or more targets asks for one name, a pattern, applied in listing order (`src/handlers/main/pane/pattern.js`): `$n` counts from 1, `$i` from 0, both zero-padded to the digits of how many there are (99 entries: `01`–`99`; 100: `001`–`100`), `$e` is each one's extension (none for a directory), `$$` a `$`. The pattern is the whole name; the prompt starts with the extension they all share (`.mkv`, the cursor before it), or `$e`. It previews the new names as the pattern is typed (`Prompt`'s new `preview`: the first two and the last), and refuses a pattern without `$n`/`$i`, an unknown token, or a name taken by an entry not being renamed. Names swapped among them go through temporary ones. Editing the names in `$EDITOR`, as vifm does, could come with 2.23's terminal takeover.
- [x] 2.9 Trash — off by default, as the user chose (deleting is permanent; no OS recycle bin). `pane.trash: true` moves deleted entries to `.vin/trash` — or `pane.trashDirectory`, relative to vin's folder — keeping both of one name there, and records where each came from in `.vin/trash.json`, by its path in the trash (`src/trash.js`, `this.trash`). The trash is mounted at `/trash`: the `trash:` scheme (`src/fs/trash.js`, mapped onto the directory; `FileSystem` maps both ends to `file:` through a provider's `realUri`, so entries move and copy in and out), shown as `trash` at the top (the list of drives on Windows, `/` elsewhere, over a real `/trash`) and typed as `/trash`. There, `pane.restore` (`r`) puts entries back where they came from — the directories on the way made again, a name taken asked about — and deleting is for good, as is `pane.emptyTrash` (no key yet; `ctrl+a` and `Delete` in `/trash` do the same), after asking. Where an entry came from isn't shown in the listing yet (2.14's status bar could).
- [x] 2.10 Long operations — background jobs with progress and cancel (`src/jobs.js`): a strip of running jobs above the message line (`JobLine` as `core.jobLine`, its green for `core.progress`), and a jobs window on `t`; quitting asks while jobs run. The conflict prompt (overwrite / merge / skip / keep both / for all) is 2.7's.
- [x] 2.11 Sorting and hidden files — by name (natural order), extension, size, modified time; ascending/descending; directories first (`pane/sorting.js`; `pane.sortBy`, `pane.sortReverse`, `pane.directoriesFirst`; the `o` menu per pane). Hidden entries — dotfiles, and the Windows Hidden attribute, from `dir /a:h /b` alongside each listing (`DirectoryEntry.hidden`) — are shown by default, faded (`pane.hidden`, the new `dim` style flag), as the user chose; `pane.showHidden` and `z a`/`z o`/`z m` hide them.
- [x] 2.12 Search — `f`/`/` searches the directory, `shift+f`/`?` it and every directory below (`pane.search`, `pane.searchTree`); the query is typed in the pane's bottom border (the `searchBar` sub-handler, a `TextField`) and the pane lists only the entries matching as it's typed, the arrows moving among them; `enter` keeps the list, `escape` goes back. A query is a wildcard pattern found anywhere in a name (`*`, `?`; smart case), or a JavaScript regular expression between `/`s (`pane/search.js`). A tree is walked breadth-first in the background without following symlinks, shown every 250 ms, and kept for the next search in the same directory; hidden directories are walked only while hidden entries are shown, the Hidden attribute coming for the whole tree from one `dir /s /a:h` on Windows (`hiddenEntries`, a new optional provider method; `readDirectory(uri, { attributes: false })` skips the per-directory one). Its matches are named by their path (`src/lib/x.js`), with that directory in a second column (`pane.location`), at most 10 000 listed and 500 000 entries walked. In the list, `n`/`shift+n` go round the matches, and opening one goes to its directory with the cursor on it; the list is a step of the history, so going back returns to it, searched again, the cursor on the entry. Operations act on the matches where they are — paste and create refuse — and search again after. The user chose no filter: the search's list is enough.
- [ ] 2.13 Preview pane — text files (first few KB, binaries detected), directory contents, file details; loads asynchronously and cancels when the cursor moves on.
- [ ] 2.14 Status bar — current path, selection count and size, details of the entry under the cursor (size, modified time, permissions/owner on Unix), free space (`fs.statfs`), messages.
- [ ] 2.15 Auto-refresh — watch the visible directories through the provider, debounced; manual refresh.
- [ ] 2.16 Help window — generated from the contribution registry, so plugin keys and commands appear automatically.
- [ ] 2.17 Session state — restore each pane's directory and view options on start, from a file in `.vin/`; a `--choose-dir`-style option (vifm has one) so a shell function can `cd` to vin's last directory on exit.
- [ ] 2.18 Startup paths — `vin [left-path] [right-path]` opens the panes there, as vifm does.
- [x] 2.20 Quitting — `core.quit` asks the UI to exit (`core`'s `quitting` state), bound to `z z` until the command line brings `:q` (6.2), when that binding goes. Ctrl+C no longer quits (Ink's `exitOnCtrlC` is off): it's copy (2.7). Key notation gained `cmd` for macOS, reported through the kitty keyboard protocol, which the TUI turns on where the terminal has it.
- [x] 2.21 Color scheme — set in `config.json5`: a `colors` section of groups by kind (`pane: { titleActive: { … } }`), validated like any option, giving each element `fg`, `bg`, `bold`, `italic`, `underline`, `inverse`, with colors as 256-color numbers, `#hex`, names, or `default` (Ink takes all of them; chalk downsamples them for terminals with fewer colors). The default is vifm's [papercolor-dark](https://github.com/vifm/vifm-colors/blob/master/papercolor-dark.vifm); its background (234) fills the whole screen, overlays included, instead of the terminal's own. Done: `Win`/`Border`/`CmdLine`/`ErrorMsg`/`CurrLine`/`LineNr` as `core`'s shared groups, `TopLine`/`TopLineSel` as the pane titles. Groups for elements not built yet are declared by the items that add them: `CurrLine`/`OtherLine` for the cursor in the active and the other pane, `Selected` (2.6), the file types for 2.2 (`Directory`, `Link`, `BrokenLink`, `Executable`, `Socket`, `Device`, `Fifo`), `StatusLine` (2.14), `JobLine` (2.10), `AuxWin` (2.13), `CmdLine`/`WildMenu` (6).
- [ ] 2.22 Sessions — named snapshots of runtime state (not configuration, which stays in `config.json5`): each pane's directory and view options, directory history (2.3), bookmarks (7.2), macros, command and search history (6, 2.12), each feature adding its part as it lands. A `session` handler with `session.save [name]`, `session.load`, `session.delete`, and a list to pick from (1.14); as `<kind>.<method>` commands they work the same from keys, `:session.save` (6), and the CLI (3.2). As in [vifm's sessions](https://vifm.info/vimdoc.shtml#vifm-sessions): one JSON5 file per session in a flat `.vin/sessions/` folder in the project root (`.vin/` holds everything vin writes as it runs, git-ignored) (so names must be valid file names); the current session is saved on exit and before switching to another, and can be left without saving; its data overrides the unnamed state 2.17 restores.
- [ ] 2.23 Open with — associations in config choosing a program by pattern (`*.md` → `$EDITOR`), and `$EDITOR`/`$PAGER` or any program marked `terminal: true` run through a terminal takeover (suspend Ink, hand over the tty, restore on exit) — the same mechanism later offered to plugins (4.7).

## 3. Context menu and CLI

- [ ] 3.1 Context menu (`Space`) — the first extension point: built-in entries (open, open with, rename, copy, move, delete, properties) plus contributed ones, shown by condition (file or directory, single or multiple selection, extension, provider); users hide, reorder, and add entries in config.
- [ ] 3.2 CLI dispatcher — yargs command modules (yargs 18 loads fine with `require()` on Node 24): `vin` opens the TUI, `vin <handler>.<command> <args>` runs a `cli: true` command, per-handler `--help`, `--version`; plain output and meaningful exit codes for scripting.
- [ ] 3.3 CLI adapters — build the context the TUI would supply (e.g. target files from arguments), so the handler method runs unchanged.
- [ ] 3.4 Resolve the ambiguity between `vin <path>` (2.18) and `vin <handler>.<command>` — `zip.zip` could be either; e.g. registered commands win, and `vin ./zip.zip` forces a path.

## 4. Plugins

- [ ] 4.1 Discovery — every plugin lives in `plugins/` in the project root; enable/disable in config.
- [ ] 4.2 Manifest schema (`plugin.json5`) — name, version, `native`/`foreign`, entry or spawn command (with per-OS overrides, e.g. `python` vs `python3`), protocol version, declared contributions (commands with surfaces, menu entries, keybindings, config options); validated with readable errors.
- [ ] 4.3 Lazy activation — contributions are read from the manifest, so menus, keybindings, and `vin --help` work without loading or spawning the plugin; it's activated on first use (like VS Code's activation events).
- [ ] 4.4 Native plugins — `require`d and registered as Handlers; a plugin that throws is disabled with a message instead of taking vin down.
- [ ] 4.5 Foreign plugin host — spawn, JSON-RPC over stdio (`vscode-jsonrpc`), protocol-version handshake, shutdown on exit, crash detection; the plugin's stderr goes to the log (stdout is reserved for the protocol).
- [ ] 4.6 Declarative UI vocabulary — list, table, form field, text, progress bar, menu entry — rendered by vin, versioned with the protocol.
- [ ] 4.7 Terminal takeover for plugins — expose the mechanism from 2.23.
- [ ] 4.8 Plugin docs and typings — a `.d.ts` for the native plugin API (per Code Conventions) and a written spec of the JSON-RPC protocol.
- [ ] 4.9 Reference plugins — `zip` as a native plugin (context-menu entries plus `vin zip.zip` / `vin zip.unzip`), and a small foreign plugin in another language (e.g. Python) to prove the protocol is language-agnostic.
- [ ] 4.10 Trust model — a separate process isolates crashes, not permissions: a foreign plugin can still do anything the user can. Decide how plugins get trusted (explicit install/enable), and whether Node-based ones run under Node's permission model (`--permission`, `--allow-fs-read`, …).
- [ ] 4.11 Name collisions — top-level handler names share one namespace (`Vin.register` rejects a duplicate), so a plugin named like a built-in or another plugin must fail with a readable message that names both sources, not crash startup; possibly an alias in config to rename one.

## 5. Network protocols

- [ ] 5.1 Decide the Architecture TBD — protocol provider as its own concept or a kind of Handler; if the latter, protocols could ship as native plugins. A foreign one can't hand over Node streams, so its reads and writes need chunks over JSON-RPC.
- [ ] 5.2 Connections — saved in config (host, port, user, auth method); SSH agent or key files, with passphrase/password prompts at connect time — secrets never stored in plain config; SFTP host keys checked against `known_hosts` (ssh2 only verifies through a caller-supplied `hostVerifier`).
- [ ] 5.3 SFTP provider (`ssh2-sftp-client`) — the full provider interface including streams; SFTP has no change notifications, so `watch` falls back to polling or manual refresh.
- [ ] 5.4 FTP/FTPS provider (`basic-ftp`) — prefer FTPS (plain FTP sends credentials in cleartext); one operation at a time per connection, so queue operations or pool connections.
- [ ] 5.5 Cross-provider copy/move — streamed between any two providers with progress and cancel; a move across providers is copy + delete; names invalid on the target OS (e.g. `:` or `?` from a Linux server to Windows) are reported or renamed.
- [ ] 5.6 Remote open/edit — download to a temp file, open it, upload on save/exit (as mc and WinSCP do); temp files cleaned up.
- [ ] 5.7 Resilience — timeouts, keep-alive, reconnect; slow listings show a loading state and can be cancelled, never blocking the UI.
